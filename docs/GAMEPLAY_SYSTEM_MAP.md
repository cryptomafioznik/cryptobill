# КАРТА ИГРОВЫХ СИСТЕМ (HTML-версия) — что с чем связано и в каком порядке считается

Дата: 2026-08-06 · Источник: `toys/chartrider.html`, read-only · Пункт 1 плана §3.
Все номера строк — на коммит `c8023dc`.

Цель документа: чтобы в Unity можно было собрать те же связи, не перечитывая 5713 строк, и чтобы
было видно, какие связи **обязательны**, а какие — историческая случайность.

## 1. ПОРЯДОК ВЫЧИСЛЕНИЙ ЗА ОДИН КАДР

```
requestAnimationFrame → loop(nowMs)                                  стр. 5464
  └─ _tmFrameBody(nowMs)
       ├─ [диспетчер по screen] — физика идёт только при screen==='play'
       └─ update()                                                   стр. 1608
            ├─ _simT += SIM_DT                     ← время симуляции (fixed-step)   1609
            ├─ if(hitstop>0) return                ← короткая заморозка удара        1610
            ├─ ввод → down / brake / leanX / jumpReq
            ├─ leanX → leanCmd → bike.rShift       ← ДОЗИРОВАНИЕ переноса веса
            ├─ rigidStep()                         ← ВСЯ ФИЗИКА, 6 под-шагов        1506
            ├─ jumpReq → bike.vy -= RB.jump                                          1643
            ├─ детект краша (конус посадки + спин)                                   1669
            ├─ детект опрокида (loopCommit + failHoldT)                         1690-1697
            ├─ genSeg() пока нужен рельеф впереди   ← только proc-режим              159
            └─ камера, частицы, HUD-состояние
```

`[КОД]` **Реальное время в физику не входит.** `physAcc += slowTS` (стр. 565, 5464 область), где
`slowTS` — безразмерный масштаб ≈ 1. Один кадр = один `update()` = один шаг `SIM_DT = 1/60`.
Следствие измерено: на телефоне ~45 FPS игра идёт в замедлении 76 %.

**Обязательное в Unity:** физика в `FixedUpdate`, независимая от частоты рендера. Это единственный
пункт §14 критериев остановки, который уже был выполнен этапом 0A под флагом `&timing=fixed`.

## 2. ЯДРО: `rigidStep()` — 6 под-шагов, что считается в каком порядке

Один вызов = один кадр. Внутри `for(s=0; s<6; s++)`, `sdt = 1/6`.

```
НА КАДР (до цикла)
  ├─ engScale  = (байк.accel/0.49)·(1+0.13·апгр.движок)         1510
  ├─ muEff     = 2.6·(байк.grip/1.40)·(1+0.15·апгр.сцепление)   1511
  ├─ thr       = lerp(thr, газ?1:0, 0.11)     ← АНАЛОГОВЫЙ ГАЗ   1514
  ├─ dRS       = rShift − предыдущий rShift   ← СКОРОСТЬ переноса веса (рывок телом)  1517
  └─ poseI     = инерция позы трюка (L=Iω)                       1518

НА КАЖДЫЙ ПОД-ШАГ
  ├─ fy += mass·grav                          ← гравитация на ЦТ            1526
  ├─ ДЛЯ КАЖДОГО КОЛЕСА wi ∈ {0=заднее ведущее, 1=переднее}
  │    ├─ позиция ступицы: wx,wy = центр ± wb·cos/sin − oy·sin/cos          1530
  │    ├─ pen = (wy + wr) − terrainAt(wx).y   ← ПРОНИКНОВЕНИЕ в линию       1531
  │    ├─ contact event на переходе pen: <0 → ≥0, время внутри под-шага
  │    │  находится линейным bracket'ом                                1535-1545
  │    └─ if(pen>0):
  │         ├─ Fn = springK·pen − springC_eff·v_n , отсечён снизу нулём     1553
  │         ├─ Ft = −v_t·rollResist            ← качение                    1556
  │         ├─ maxF = muEff·Fn                 ← конус для тормоза/бокового 1557
  │         ├─ FnDrive:
  │         │    DRV_ON=true (дефолт) → сглаженный РЕАЛЬНЫЙ Fn, пол 10 % mg 1559
  │         │    DRV_ON=false (legacy) → max(Fn, 0.85·mg)  ← ПОЛ НАГРУЗКИ   1561
  │         ├─ ведущее + подъём > climbFrom → FnDrive ×= эндуро-бонус       1562
  │         ├─ maxFd = muEff·FnDrive
  │         ├─ газ:    Ft += min(engine·engScale·thr, maxFd)                1564
  │         ├─ тормоз: Ft += −sign(v_t)·brakeF ; на месте → реверс          1565
  │         ├─ кламп Ft в [−loCap, maxFd]                                   1567
  │         └─ силы и момент от Fn и Ft на шасси                      1554,1568
  ├─ ЕСЛИ НА ЗЕМЛЕ
  │    ├─ момент от веса райдера: (rShift·leanGround + dRS·leanYank)·I·leanK 1572
  │    ├─ PD-стабилизатор переда к углу склона     ← гаснет на дизайн-крутом 1586
  │    ├─ стабилизация при наклоне на крутом       ← гаснет там же          1587
  │    ├─ подушка у грани вилли                    ← гаснет там же          1588
  │    ├─ задний тормоз опускает нос на вилли      ← НЕ гаснет никогда      1589
  │    └─ anti-loop возврат от предела             ← нос-вверх гаснет       1590
  ├─ ЕСЛИ В ВОЗДУХЕ
  │    ├─ авторитет вращения ∝ времени полёта (25 % → 100 % за 14 кадров)   1573
  │    ├─ момент от РЫВКА веса (не от статического положения)               1574
  │    └─ авто-выравнивание к углу будущей поверхности + гашение спина 1580-1582
  └─ интегрирование: v += F/m·sdt ; x += v·sdt ; angV += tq/(I·poseI)·sdt ; ang += angV·sdt  1591-1593

ПОСЛЕ ЦИКЛА (раз на кадр)
  ├─ drag: vx ×= onGround ? rollDrag : airDrag       ← ПОТОЛОК СКОРОСТИ     1595
  ├─ «вилли ≠ турбо»: компенсация потери качения переднего                  1596
  ├─ angV ×= angDamp ; кап |angV| ≤ avMax ; на вилли кап ≤ wheelieAvMax 1597-1601
  └─ bike.onG = onGround                                                    1603
```

### 1.1 Ключевая причинная петля игры — её надо сохранить дословно

```
   ГАЗ ──→ момент мотора на заднем колесе ──→ момент, задирающий нос
                                                      │
                            нос вверх ──→ реальный Fn на переднем ↓
                                                      │
              ВЕС ВПЕРЁД ←── контр-приём игрока ───────┘
                    │
                    └──→ переднее загружено ──→ нос держится, НО заднее разгружено ──→ тяги меньше
                                                                    │
                                                  ВЕС НАЗАД ←───────┘  (driveTrade 0.20)
```

`[ВЫВОД]` Это и есть «окно навыка»: два конкурирующих требования к одному органу управления.
Измерено: реактивная политика веса против нейтральной даёт **+46.2 %** дистанции при тяге от
реального прижима и только **+23.7 %** при поле нагрузки. **В Unity эта петля — приёмочный
критерий, а не деталь реализации.**

## 3. ГДЕ ЖИВУТ ЧИСЛА (для пункта 4 плана)

| Блок | Строки | Что в нём | Судьба |
|---|---|---|---|
| `RB` | 709-730 | **Настоящая физика**: масса, инерция, геометрия, пружина, µ, мотор, тормоз, помощники вилли, углы краша, демпферы, под-шаги | ядро `BikeTuningProfile` |
| `TUNE` | 582-695 | 60+ ручек «фила»: гравитация, тяга, drag, тормоз, генератор рельефа (gap/kick/mega/whoop/ledge/mud/drop/climb), камера, волна | расщепить: физика → профиль байка, рельеф → профиль трассы |
| `PHYS` | 697-701 | Прокси к `TUNE` + геометрия `DX/DY` | **почти мёртвый**: живые чтения только `PHYS.DX` в рендере (стр. 2315, 2538, 3003) |
| `PHX_DEF` | 549-563 | 13 коэффициентов помощников, 1.0 = сток, 0 = выключен | ПОРТ механизма 1:1 |
| `DRV_TUNE` | 526 | `fnSmooth 0.22`, `floorFrac 0.10` — фильтр реального прижима | ПОРТ идеи, перемерить числа |
| `CANDLE_TUNE` | 114-120 | Свеча → крутизна рельефа, 5 множителей | профиль трассы |
| `VS` | 3570-3603 | Дизайн-трасса: 33 узла, гэп, финиш, 2 чекпоинта, `physics`-профиль уровня, камера | данные 1:1 |
| `VSD` | 3634 | Косоугольная дорога — литеральные константы | выбросить |
| `PSP` | 777 | Перспектива — недостижима (`PSP_ON=false`) | выбросить |
| `UPGRADES`/`BIKES`/`SKINS` | 844-1012 | Экономика | не ночью |
| `EVENTS` | 139-143 | Рыночные события | не ночью |

`[ВЫВОД]` Числа физики размазаны по **четырём** блокам (`RB`, `TUNE`, `PHX_DEF`, `DRV_TUNE`) плюс
пятый на уровне трассы (`VS.physics`). Единый `BikeTuningProfile` — правильная цель, но при
слиянии надо помнить, что `VS.physics` **переопределяет** `PHX_DEF` для конкретного уровня
(стр. 1156). Значит в Unity нужны два объекта: профиль байка и профиль-оверрайд уровня.

## 4. ТРАССА: ДВА НЕЗАВИСИМЫХ ИСТОЧНИКА ОДНОГО МАССИВА

```
                    ┌─ trackSource='proc'   → genSeg() поузлово: pickRegime → свеча → рельеф
   terr[] ←─────────┤                          + фичи (gap/kick/mega/whoop/climb/...)
   (узлы по 26 px)  │
                    └─ VSLICE=true          → buildVSliceTerr(): vsHeight(x) по 26 px, 443 узла
                                                (trackSource='ticker' → тот же массив из OHLC)
                              │
                              ▼
                    terrainAt(x) → {y, ang}   ← ЕДИНСТВЕННЫЙ вход физики в трассу
                              │                  линейная интерполяция, ang = atan2(Δy, 26)
                              ▼
                    rigidStep(): pen = (wy+wr) − terrainAt(wx).y
```

`[ВЫВОД]` Архитектурно это **правильно и это надо сохранить**: физика знает о трассе ровно одну
функцию `terrainAt(x) → (высота, уклон)`. Подмена источника (процедурный / дизайн / реальный
график) тривиальна и не трогает физику. В Unity аналог — `EdgeCollider2D`, наполняемый из
любого источника, плюс отдельный сервис «высота и уклон в точке x» для помощников управления
(они читают уклон впереди, стр. 1580: `terrainAt(bike.x + max(20, vx·8)).ang`).

`[КОД]` **Ловушка:** `buildVSliceTerr` ставит `baseY = H*0.6` (стр. 3624) — абсолютная высота
трассы зависит от высоты окна браузера. Форма не зависит, но абсолютные Y — да. Это родня уже
оплаченной ловушки «`NO_TILT` даёт 89 % при 430×932 и 87.3 % при 1280×800». В Unity мир не должен
знать о вьюпорте вообще.

## 5. СОБЫТИЙНАЯ МОДЕЛЬ КОНТАКТОВ — лучшее, что есть в проекте

```
ФИЗИКА (авторитет)                          АНИМАЦИЯ (потребитель)
  rigidStep, под-шаг s
    pen переходит <0 → ≥0
        │
        └─→ _emitContact(...)  ────────→  _cev[] (очередь, кап 64)
              id, simTime, wheel R/F,           │
              точка, нормаль, скорость ДО,      ├─→ риг выпивает события
              normalSpeed, airDuration,         │
              gapPrev, gapCur                   └─→ window.__cevLog (полный поток для приёмки)
```

`[КОД]` Стр. 537-541 и 1532-1545. Время касания внутри под-шага находится линейным bracket'ом по
`prevPen`/`pen`. `[ВЫВОД]` Граница правильная: физика определяет касание **ровно один раз**, а
анимация больше не переоткрывает столкновение из разреженных render-сэмплов (это давало
`tContact ±21 мс` и разное число событий 2/2/1 между прогонами).

**В Unity:** `OnCollisionEnter2D` даёт то же, но со своим ID. Отдельный лог для приёмки
(`__cevLog`) — сохранить: очередь выпивается анимацией, а тестам нужен полный поток.

## 6. РЕЖИМЫ И ФЛАГИ, КОТОРЫЕ МЕНЯЮТ ФИЗИКУ

| Флаг | Как включается | Что меняет | Судьба |
|---|---|---|---|
| `VSLICE` | `?level=vertical-slice` | дизайн-трасса + `VS.physics` поверх `PHX_DEF` | ПОРТ как «сцена уровня» |
| `DRV_ON` | дефолт **true**, `?drive=legacy` выключает | тяга от реального прижима ↔ пол нагрузки | **дефолт = real, легаси не переносить** |
| `TIMING_FIXED` | `?timing=fixed` | реальное время в аккумуляторе | в Unity по умолчанию |
| `trackSource` | `'proc'` / `'ticker'` | источник рельефа | ПОРТ |
| `shortMode` | localStorage | трасса по перевёрнутому графику | не ночью |
| `PSP_ON` | константа `false` | ракурс ¾ | выбросить |
| `CORE_TEST_MODE` | константа `false` | отключает рыночные события | заменяется чистой тест-сценой |
| `wheelieAssist` | настройка | подушка у грани вилли | ПОРТ как поле профиля |
| `trackSource!=='ticker'` | внутри решателя, стр. 1571, 1585 | **`designHard`: на дизайн-трассе прощение управления снимается, на реальном графике — нет** | ПОРТ, но см. ниже |

`[ВЫВОД]` Последняя строка — скрытая связь, которую легко потерять: **сложность управления зависит
от источника трассы**. На реальном крипто-графике байк прощает больше, на авторской трассе — меньше.
Это решение зашито в две строки решателя (1571, 1585), а не в конфиг. В Unity это должно стать
явным полем профиля уровня, иначе оно потеряется молча.

## 7. ЧТО ИЗ ЭТОЙ КАРТЫ ОБЯЗАТЕЛЬНО ДЛЯ ПЕРВОГО ЗАПУСКА В UNITY

Минимум, при котором байк едет и петля §2.1 работает:

1. `terrainAt`-эквивалент: полилиния 26 px + функция «высота и уклон в x».
2. Шасси + 2 колеса, контакт, пружина, тяга ограниченная **реальным** прижимом.
3. Момент от переноса веса, включая рывок (`dRS`), не только положение.
4. Пять помощников из §2: стабилизатор переда, подушка вилли, anti-loop, задний тормоз на вилли,
   авто-выравнивание в воздухе — с коэффициентами `PHX` и гашением на крутом подъёме.
5. Детект опрокида с выдержкой `failHoldT` и детект краша по конусу посадки.
6. Аналоговый газ и аналоговый наклон.
